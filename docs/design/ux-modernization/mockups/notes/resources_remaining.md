## Capture gap (read before using this as a design ref)

Two things could not be produced in this sandbox and need a follow-up:

1. **Live screenshots of the running app** (the issue's Task 2). This sandbox has no C++ toolchain (no `cmake`/`g++`/Qt6) and no GUI-driving capability (no `computer-use`-equivalent tool, no display). The prior epic's equivalent gap (docker/apt_source_manager/gnome_settings — see `CAPTURE_NOTES.md` "Pages with no live capture anywhere") was resolved by whoever ran that session using either the `ScreenshotTests` harness on a homelab host or `computer-use` + `screencapture` on a real desktop. Neither is available here.
2. **Rasterizing `pages/resources_remaining.html` to PNG.** The repo's own render pipeline (`scripts/design/render_mockups.sh`, Playwright + headless Chromium) is otherwise usable — Node/npx and `playwright` are present and the Chromium binary downloads fine — but the downloaded `chrome-headless-shell` cannot launch: it's missing `libglib-2.0.so.0`, `libnss3.so`, `libX11.so.6`, and a dozen other shared libraries, and this sandbox has no root/`apt-get` access to install them (`E: Could not open lock file /var/lib/dpkg/lock-frontend ... are you root?`). This is a sandbox gap, not a repo problem: `pages/resources_remaining.html` is a normal addition to the existing `pages/*.html` glob and `scripts/design/render_mockups.sh` will pick it up unmodified on any host that already has the render pipeline's system deps (CI, or a developer machine).

Both gaps are handed to DevOps as a follow-up (see the linked child issue in the SSO-14436 comment thread) — either can produce the `renders/resources_remaining_{dark,light}.png` files; live capture is the stronger evidence if feasible, otherwise running the existing render script against the HTML committed here is sufficient to close the AC bullet.

## No invented data — per-tile disclosure

- Memory, Disk Temperature: axis is a fixed-range `QValueAxis` (`setYMax(100)`), so the 100.0/75.0/50.0/25.0/0.0 (Y) and 60.0/45.0/30.0/15.0/0.0 (X) labels are fixed chrome, safe to reproduce exactly (same values as the already-approved CPU/GPU charts, which also fix Y max to 100).
- CPU Pressure Stall: axis defaults to `setYMax(1.0)` before any data arrives (same shape as CPU Load Averages, itself approved with 1.00/0.75/0.50/0.25/0.00), reproduced on that basis; the live max auto-scales upward once real PSI samples arrive, which is out of scope for a static empty-state reference.
- Network: `QCategoryAxis` labels are populated only by `setCategoryAxisYLabels()` after live data — same situation as the already-approved "History of Disk Read Write" card, whose notes explicitly withheld invented axis numerics. Same precedent applied here: chrome + empty plot only, no axis text.
- Disk Temperature legend: series count is drive-count-dependent (`ensureDiskHealthChart`), not fixed. Rendered as 1 representative swatch with an explicit "dynamic, not fixed chrome" caption rather than asserting a specific drive count.
- OOM Kills: the state/totals/empty-state strings shown are the widget's own hardcoded copy (`buildUI()`/`onOomdUpdated()` literal `tr()` strings), not sampled from a live host — the "systemd-oomd: active." state line and zero totals are one illustrative branch of several (`onOomdUpdated` has ~6 different state-line branches depending on `loadState`/`activeState`).
- Disk Usage Analysis: the tool name/description/status shown ("Disk Usage Analyzer (Baobab)", "Status: Installed") is one of ~13 `detect()`-driven states (`updateUi()` switch, `disk_usage_launcher_widget.cpp:316-436`) — the common GNOME-desktop default — not a live capture of any specific host's detected tool.
